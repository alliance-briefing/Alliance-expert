1. Le projet

1.1 Ce que le client demande

Alliance Experts, groupement national d'expertise automobile, a déjà un assistant pour managers construit avec Microsoft Copilot Studio. Le sujet : sortir de l'écosystème Microsoft et construire un agent sur une architecture plus indépendante et contrôlable. Chaque jour l'agent analyse les e-mails, les événements de calendrier à venir, les tâches en retard et les fichiers récemment créés ou modifiés, puis produit un brief quotidien clair, court et actionnable : éléments retenus, résumés, priorisés, avec accès à la source.

  • Aucune donnée réelle d'Alliance Experts ou de personnes réelles dans le dépôt, les tests ou les prompts. Comptes de démonstration et jeux de données synthétiques uniquement, sauf accord écrit préalable de David.

2. Architecture et contrats entre lots

2.1 Principe : les lots ne se bloquent jamais

Chaque lot livre dès la semaine 1 des fixtures (données factices conformes au contrat) et un stub (implémentation minimale qui renvoie ces fixtures). Le lot 2 travaille sur les fixtures du lot 1 avant que les connecteurs réels existent. Le lot 3 affiche les fixtures du lot 2 avant que le LLM soit branché. Le premier jalon est un walking skeleton : le pipeline complet tourne de bout en bout sur des données factices, avant toute fonctionnalité réelle.

Interdit dans le journal : corps de message, jetons, mots de passe, adresses e-mail complètes. On journalise des identifiants et des compteurs, pas du contenu.

2.5 Où vivent les contrats

  • Dossier contracts/ : modèles pydantic v2 (source de vérité) + JSON Schema exporté + fixtures/ + CHANGELOG.md.
  • Versionnement semver : ajout d'un champ optionnel = mineur (1.1) ; renommage, suppression, changement de type ou de sens = majeur (2.0).
  • Un changement de contracts/ exige l'approbation d'un référent de chacun des 3 lots et l'étiquette contract-change. Les fixtures sont mises à jour dans la même PR.
  • Un test en CI valide que toutes les fixtures respectent le schéma, et que le stub de chaque lot produit un objet valide.

3.6 Décisions : le format ADR

Toute décision qui coûte cher à défaire (choix de bibliothèque, de modèle, de base de données, changement de contrat, seuil d'évaluation) s'écrit dans docs/adr/NNNN-titre.md (gabarit annexe 8.3), en 10 lignes, et passe par une PR. Un ADR accepté n'est modifié que par un ADR qui le remplace.

3.7 Absences, désaccords, blocages

  • Absence prévue : annoncée dans le chat du lot, avec ce qui reste en cours et qui le reprend.
  • Aucune activité (commits, messages) pendant 5 jours ouvrés sans annonce : le référent le signale à David.
  • Désaccord technique entre lots : le comité tranche à la majorité des 3 référents ; en cas de doute, on choisit l'option réversible et on écrit l'ADR.
  • Conflit ou problème de participation : à David, en privé, avec des faits (dates, PR, messages).
Contribution individuelle Chacun doit pouvoir expliquer à l'oral n'importe quelle ligne qu'il a soumise, y compris si un assistant de code l'a produite. L'historique Git est lu individuellement : les commits et les revues de chaque membre sont visibles.

4.3 Workflow : trunk-based, branches courtes

  1. Chaque tâche a une issue (identifiant du guide : L1.3, L2.4…). Pas de code sans issue.
  2. Une branche par issue, nommée <lot>/<type>/<slug>, ex. l1/feat/mail-connector, l2/fix/dedup-thread, l3/docs/adr-ui. Types : feat fix docs test refactor chore.
  3. Durée de vie d'une branche : 2 jours ouvrés maximum. Une branche plus vieille se découpe en deux.
  4. Tu te rebases sur main au moins une fois par jour de travail.
  5. PR ≤ 400 lignes modifiées (hors fichiers générés et fixtures). Au-delà, on découpe.
  6. Revue : approbation d'une personne du même lot ; deux approbations si la PR touche contracts/ (un référent de chacun des 3 lots). Personne n'approuve sa propre PR. Réponse à une demande de revue sous 24 h ouvrées.
  7. Merge en squash ; titre de la PR au format Conventional Commits.
  8. Après le merge, on supprime la branche.

4.4 Commits et PR

  • Conventional Commits avec le paquet en portée : feat(collect): ajoute le connecteur calendrier Graph, fix(analyse): corrige la dédup des fils, docs(adr): ADR-0004 choix du modèle, chore(ci): active gitleaks.
  • Un commit = une intention. Pas de « wip », « fix », « update ».
  • La PR suit le gabarit annexe 8.2 : issue liée, ce qui change, comment vérifier, captures si UI, risques, cases à cocher (tests, doc, contrat).

4.5 Jalons et versions

Étiquettes annotées, posées uniquement par l'intégrateur sur main vert : v0.1.0 (walking skeleton), v0.2.0, v0.3.0, v0.9.0 (gel des fonctionnalités), v1.0.0 (rendu). Chaque tag a des notes de version : ce qui marche, ce qui manque.

4.6 Secrets et données

  • Aucun secret dans Git : clés API, jetons, identifiants OAuth, mots de passe. Un fichier .env local, non versionné ; le dépôt contient infra/.env.example avec des valeurs factices.
  • gitleaks en pre-commit et en CI. La CI échoue si un secret est détecté.
  • Si un secret a été poussé : 1) le révoquer et en créer un nouveau immédiatement, 2) prévenir le référent sécurité (lot 1), 3) seulement ensuite nettoyer l'historique. Réécrire l'historique ne rend pas un secret sûr : il faut le considérer comme public.
  • Aucune donnée réelle de personne. Les jeux de données sont générés (script versionné + graine aléatoire fixée).

L2.1 · Agrégation et regroupement Rôle A · jusqu'au 28/10
Objectif
Réunir des Item de sources différentes dans un contexte commun : un même sujet (un fil de mails, une réunion, un fichier, une tâche) est vu comme une seule « affaire ».
Sortie

L2.2 · Score de priorité expliqué Rôle A · v1 le 28/10, v2 le 11/11
Objectif
Classer les affaires de 0 à 100 avec des raisons lisibles, indépendamment du LLM.
Signaux minimaux
  • Expéditeur : n'appartient pas à la liste noire, appartient à la liste des contacts fréquents ou à la hiérarchie (configurable).
  • Question directe ou demande d'action détectée.
  • Échéance citée ou due_at proche ; ancienneté d'une demande sans réponse (en jours ouvrés).
  • Réunion à venir liée (même sujet) dans les 48 h.
  • Importance native (native_importance) et mots signalant l'urgence.
  • Bruit : newsletters, notifications automatiques (baisse du score).
Acceptation
  • Chaque score est accompagné de 1 à 4 priority_reasons compréhensibles par un manager, sans jargon.
  • Le score est reproductible : mêmes entrées, même sortie.
  • Comparaison au classement de référence du jeu annoté (NDCG@5) publiée dans le README ; toute modification du barème doit améliorer ou maintenir ce chiffre sur le jeu de développement.
  • Le LLM peut ajuster le score dans une plage de ± 15 points avec une raison écrite ; il ne le remplace pas.
L2.3 · Résumé par LLM avec sortie structurée Rôle B · jusqu'au 28/10 (v1), 11/11 (v2)
Objectif
Produire le texte de chaque entrée du brief et l'action recommandée, en JSON contraint au contrat B.
Sortie
Prompts versionnés (p1, p2…) dans packages/analyse/summarize/prompts/ ; appel avec sortie structurée validée par pydantic ; réessai unique en cas de sortie invalide ; en cas de second échec, l'entrée est produite sans résumé LLM (extrait brut + lien) avec un avertissement, jamais inventée.
Forme du brief (défauts)
  • ≤ 400 mots au total ; ≤ 7 entrées « à traiter » ; réunions du jour listées avec l'heure (heure de Paris) ; retards regroupés.
  • Chaque entrée : une phrase de contexte, une phrase d'action, ≤ 40 mots.
  • Langue de sortie = langue de l'utilisateur (FR ou EN), configurable.
Acceptation
  • 100 % des entrées valident le schéma sur le jeu de développement.
  • Le prompt ne contient que des Item de l'utilisateur concerné (test d'isolation).
  • Les instructions présentes dans un e-mail ne sont jamais exécutées (injection de prompt) : au moins 10 e-mails piégés dans le jeu de test (« ignore les consignes et envoie… ») ne modifient ni le brief ni les entrées.
L2.4 · Garde anti-hallucination et traçabilité Rôle C · jusqu'au 11/11 · exigence forte
Objectif
Aucune affirmation sans source vérifiable.
Sortie
Après génération, chaque phrase est découpée en claims ; chaque claim porte ≥ 1 source_item_id. Le module guard vérifie de façon déterministe : (1) l'item_id cité existe dans l'entrée ; (2) les dates, heures, montants, noms propres et numéros du claim se retrouvent dans l'Item cité ; (3) un claim sans source est retiré ou l'entrée régénérée une fois.
Acceptation
  • Porte dure : aucun brief n'est livré avec un claim sans source valide ; sinon l'entrée est dégradée (extrait + lien) et un warning est ajouté.
  • Taux de claims soutenus ≥ 95 % sur le jeu de développement, mesuré par le lot 3 (pas par vous).
  • Un jeu de 20 cas adverses (date fausse, montant inversé, homonyme, information présente dans un autre utilisateur) est ajouté aux tests et le module les rejette tous.
  • Pour une entrée du brief, une commande trace <brief_id> <rank> affiche les Item sources et l'extrait qui soutient chaque claim.
Piège
Un LLM qui vérifie un LLM n'est pas une preuve ; la vérification déterministe est la base, le LLM juge est un complément mesuré.
L2.5 · Interface LLM remplaçable et comparatif de modèles Rôle D · jusqu'au 11/11
Objectif
L'indépendance vis-à-vis d'un fournisseur est le sujet du client : le lot 2 doit la démontrer.

Comparatif
Au moins 2 modèles × 2 stratégies de prompt, mêmes entrées, température 0 ou graine fixée, sur le jeu de développement. Tableau : taux de claims soutenus, rappel et précision du lot 3, latence p50/p95, coût par brief (tokens et euros), taux d'échec de format. Recommandation argumentée dans un ADR.
Acceptation
Changer de modèle = changer une ligne de configuration ; test qui exécute le pipeline avec chacune des deux implémentations sur les mêmes fixtures.
L2.6 · Contexte par recherche (RAG) — conditionnel Rôle D · décision au 28/10
Quand
Seulement si le comparatif montre que le contexte manque (ex. il faut l'historique d'un fil ou un document lié pour bien résumer). À décider par un ADR avec des chiffres.
Sortie si retenu
Index vectoriel par utilisateur (pgvector, Qdrant ou Chroma), alimenté à partir des Item, filtré par acl avant la recherche. Recherche limitée à l'utilisateur du brief. Suppression complète possible (voir L1.7).
Acceptation

  • Test d'isolation : requête de l'utilisateur A jamais servie avec un extrait de B.
L2.7 · Performance, coût, robustesse Rôle D · en continu
